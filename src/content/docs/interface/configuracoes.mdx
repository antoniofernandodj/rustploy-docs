**Settings** (no rodapé do menu lateral) tem cinco abas: **Web Server**, **Git**,
**Infra as Code**, **Manutenção** e **Atualizações**.

## Web Server

<Shot
  src={web}
  alt="Aba Web Server com a URL pública da API, o token de conexão e o comando para conectar um agente do Claude Code. Os endereços e o token foram borrados."
  caption="Aba Web Server. Os valores foram borrados nesta imagem."
/>

Três blocos, cada um com **Copiar**:

| Bloco | O que é |
|---|---|
| **URL PÚBLICA DA API** | a base dos **webhooks** dos serviços e do callback do OAuth. Vem de `[api].domain` e da porta. Para mudá-la, configure `api.domain` e reinicie o daemon |
| **TOKEN DE CONEXÃO** | o texto em base64 de `host:porta::token`, o que se cola no [login](/interface/entrar/) e que um agente de IA usa. Também fica em `[api].connection_token` no `config.toml` |
| **CONECTAR UM AGENTE DE IA (MCP)** | três botões Copiar, para Claude Code (`claude mcp add …/mcp`), Codex (bloco para o `~/.codex/config.toml`) e Gemini CLI (`gemini mcp add …`), todos já com o token. Veja [Conectar o Claude Code, Codex e Gemini](/agentes/conectar-claude-code/) |

<Aside type="danger">
  O token de conexão **vale tanto quanto o token de administrador**. Não o compartilhe,
  e não publique prints desta tela sem borrar.
</Aside>

Mais abaixo, role a tela, ficam o **E-MAIL LET'S ENCRYPT (HTTPS AUTOMÁTICO)** e o
**DOMÍNIO DO REGISTRY (EXPOSIÇÃO PÚBLICA)**. Os dois exigem reiniciar o daemon.

## Git

<Shot
  src={git}
  alt="Aba Git sem contas conectadas, com a escolha entre Gitea e GitHub, os campos Nome e Base URL, o método OAuth2 ou token e os campos Client ID e Client Secret."
  caption="Aba Git: conectar uma conta."
/>

Aqui você conecta contas **GitHub** ou **Gitea** uma vez e as usa em todos os
serviços e jobs. **CONTAS CONECTADAS (N)** lista as existentes.

Para **conectar**:

1. Escolha **Gitea** ou **GitHub**.
2. Informe um **NOME** (só um rótulo) e, para Gitea ou GitHub Enterprise, a **BASE URL**. No GitHub.com deixe em branco.
3. Escolha o **MÉTODO**: **OAuth2** ou **Token (PAT)**.
4. Com **OAuth2**, informe o **CLIENT ID** e o **CLIENT SECRET** de um aplicativo OAuth criado no provedor.
5. Clique em **Conectar conta**.

<Shot
  src={gitOauth}
  alt="Parte de baixo da aba Git mostrando a Redirect URI com botão Copiar, a instrução para o Gitea e os botões Conectar conta e Atualizar lista. A URI foi borrada."
  caption="O final do formulário: a Redirect URI. (Borrada nesta imagem.)"
/>

No OAuth, a tela mostra a **REDIRECT URI**: copie-a com **Copiar** e cole no
aplicativo OAuth do provedor (no Gitea: *Settings → Applications*; no GitHub:
*Settings → Developer settings → OAuth Apps*, campo *Authorization callback URL*).
Ao clicar em **Conectar conta**, o navegador abre para você autorizar.

Com **Token (PAT)**, cole um *Personal Access Token* com permissão de leitura dos
repositórios (escopo `repo`). **Atualizar lista** recarrega as contas.

Detalhes e o uso nos serviços: [Fazer deploy a partir de Git](/guias/git/).

## Infra as Code

<Shot
  src={iac}
  alt="Aba Infra as Code com os blocos Exportar e Importar, as opções prune e disparar deploy e os botões para exportar e importar um arquivo zip."
  caption="Aba Infra as Code."
/>

| Bloco | O que faz |
|---|---|
| **Exportar para um .zip…** | gera um `.zip` com `rustploy.yml` e `rustploy.vars.toml` no lugar que você escolher. Os valores das variáveis ficam só no TOML; **secrets nunca saem do daemon** |
| **Importar de um .zip…** | lê um `.zip` do mesmo formato, com **exatamente um** `.yml` e um `.toml` na raiz |

Na [web UI](/interface/web-ui/) a aba é a mesma: **Exportar para um .zip…** baixa o arquivo pelo
navegador (`rustploy-infra.zip`) e mostra os dois textos para conferir ou copiar, e a importação aceita o `.zip` pelo
seletor de arquivo **ou** o texto colado. Nas duas interfaces o app **pede confirmação** antes de aplicar.

Opções da importação:

| Opção | Efeito |
|---|---|
| **Remover serviços ausentes do manifesto (prune)** | apaga os serviços que não estão no manifesto |
| **Disparar deploy dos serviços criados/alterados** | faz o deploy depois de sincronizar |

Se faltar o valor de alguma variável usada no YAML, a importação é **cancelada antes
de aplicar qualquer coisa**, e a mensagem diz qual variável falta, rotulada com o
escopo (por exemplo `Chiquitos/api: APP_PORT`). Detalhes em
[Infra as Code](/guias/infra-as-code/).

## Manutenção

<Shot
  src={manutencao}
  alt="Aba Manutenção com a limpeza automática ativada, frequência diária às 03:00, e as opções de containers parados e imagens sem uso marcadas."
  caption="Aba Manutenção, início do formulário."
/>

Aqui fica a **limpeza automática do Docker**. Ela vem **desligada** e **não remove
nada** até você marcar pelo menos um recurso e ativar.

1. Ligue **Ativar limpeza automática**.
2. Em **FREQUÊNCIA**, escolha **A cada N horas**, **Todo dia** ou **Toda semana** e o **HORÁRIO**.
3. Em **O QUE LIMPAR**, marque os tipos.
4. Clique em **Salvar**. **Executar agora** roda na hora.

<Aside type="caution" title="O horário que você digita é UTC">
  O campo **HORÁRIO** é em **UTC**. A linha **Próxima execução agendada** mostra o
  horário no **seu fuso**: na imagem acima, `03:00` aparece como `15/10 00:00`
  (UTC−3). Use essa linha para conferir.
</Aside>

<Shot
  src={manutencaoFim}
  alt="Final da aba Manutenção com redes sem uso e cache de build marcados, o aviso de volumes em vermelho, os botões Salvar e Executar agora e a última execução."
  caption="Aba Manutenção, final: volumes, botões e última execução."
/>

| Opção | Efeito |
|---|---|
| **Containers parados** | remove os containers parados |
| **Imagens sem uso** | por padrão só as *dangling*. **incluir todas as não usadas** inclui também as com tag |
| **SÓ IMAGENS CRIADAS HÁ MAIS DE (HORAS)** | padrão **168**. `0` não filtra. O Docker olha a data de criação, não a do último uso |
| **Redes sem uso** | remove redes sem containers |
| **Cache de build** | remove o cache sem uso |
| **MANTER O CACHE USADO NAS ÚLTIMAS (HORAS)** | padrão **168**. `0` apaga todo o cache sem uso |
| **Aquecer os builds depois da limpeza** | ligado por padrão. Depois de limpar, reconstrói a imagem de cada serviço com repositório Git ou zip, **um de cada vez**, na fila de deploy, para o primeiro deploy do dia não pagar o build inteiro. Cada serviço mostra o selo **quente / frio** |
| **Volumes sem uso** | **cuidado** |

<Aside type="danger" title="Volumes">
  *"Volumes sem uso criados por fora do rustploy podem conter dado que ninguém
  recriaria sozinho."* Deixe desmarcado a menos que tenha certeza.
</Aside>

No final, **ÚLTIMA EXECUÇÃO** mostra quando rodou e o que liberou (containers, imagens,
redes, cache de build). Mais em [Limpeza do Docker](/guias/limpeza-docker/).

## Atualizações

Mostra se há uma versão mais nova do **daemon** do que a que está rodando no servidor e, se o servidor foi instalado
pelo `.deb`, atualiza o daemon com um botão.

| Campo | O que é |
|---|---|
| **Versão instalada** | a versão do `rustployd` que o app está usando agora |
| **Última versão** | a última release **estável** publicada no GitHub (`antoniofernandodj/rustploy`) |
| **Verificado em** | quando o daemon consultou o GitHub de fato (pode ser de algumas horas atrás) |

Quem consulta o GitHub é o **daemon**, não o app: a pergunta é "o servidor está desatualizado?". O resultado fica
em cache por **6 horas** (o GitHub limita a API anônima a 60 consultas por hora por IP) e o botão **Verificar
atualizações** ignora o cache, mas no máximo uma vez por minuto. O app também consulta uma vez ao conectar, para a
aba já abrir preenchida.

Quando há versão nova, a aba mostra **Atualizar daemon**. Antes de agir ela pede confirmação (e, se há deploy em
andamento ou na fila, pergunta de novo). O daemon guarda um snapshot do banco, baixa o pacote e a assinatura e entrega a um
helper root, que só instala o que estiver **assinado** pelo projeto; depois da instalação o serviço precisa ficar estável,
ou os binários anteriores voltam sozinhos. **Reverter para a versão anterior** restaura os binários do backup da última
atualização. Os detalhes estão em [Atualizar o Rustploy](/instalacao/atualizar/#atualizar-pelo-settings) e o modelo de
segurança em [o helper de atualização](/operacao/seguranca-do-servidor/#o-helper-de-atualização).

O daemon reinicia no meio (os containers dos serviços continuam rodando). No app desktop a janela volta ao login: entre de
novo e a aba mostra o resultado (por exemplo "Atualizado para 0.1.11" ou a causa de uma falha). Na web UI o progresso aparece
ao vivo. Sem o helper (instalação sem `.deb` ou sem systemd) a aba mostra, em vez do botão, o comando de instalação com
**Copiar** e o endereço das notas da release.

Se a VPS não alcança o GitHub, a aba mostra a causa (sem internet, limite de consultas, nenhuma release publicada).
Para desligar a consulta, ou trocar o repositório, use a seção `[update]` do `config.toml`:

```toml
[update]
enabled = true                         # false: o daemon nem consulta o GitHub
repo = "antoniofernandodj/rustploy"    # dono/nome
cache_hours = 6
allow_agent_apply = false              # true: o agente MCP também pode atualizar
```

A web UI tem a mesma aba, com os mesmos campos.
