<Aside type="danger" title="Read before connecting an agent">
  By default the API token is a **single, unscoped bearer**. Whoever has it creates projects, starts containers and takes
  stacks down. To give an agent a limited key, generate a [master key](#master-key-and-visitor-key). Through **MCP** the agent does not receive secret values (see below), but the same
  token on `/api/rpc` — which the GUI and the web UI use — does not go through that protection.
</Aside>

## What the agent can do

Everything the administrator can. The agent **sees** the token, because it is what authenticates. Destructive
commands **do not ask for confirmation** on the server: `ServiceDelete`, `Prune*`, `Remove*`, `StopAllManaged`,
`RegistryRepoDelete`.

## What the agent (via MCP) never receives

MCP and `rpc` go through a layer that **hides secrets** before answering. It is a safety net against accidental leaks;
it is **not** a vault.

- **Secret values**: `SecretReveal` is forbidden to the agent.
- **Plain variables that look secret**: if the key contains `PASSWORD`, `PASS`, `SECRET`, `TOKEN` or `KEY`
  (`POSTGRES_PASSWORD`, `S3_ACCESS_KEY_ID`…), the value arrives as `***`. It is generous on purpose: it hides even
  `VAPID_PUBLIC_KEY`.
- **Passwords in URLs**: any `user:password@host` arrives as `user:***@host`, including the internal URL from
  `ServiceConnectionInfo`.
- **Exports**: the `.env` and the YAMLs follow the same rule.
- **Forbidden to the agent**: `SecretReveal`, `SecretMove` with `SecretToEnv` (it would become a plain variable),
  `RegistryTokenCreate` (returns the token in clear text) and `ServiceExport` with values.
- **Editing without corrupting**: if the agent sends back a spec containing `***` (the `ServiceGet` → edit →
  `ServiceUpdate` path), the daemon **restores the real value**. If there is no previous value, it refuses.

This does **not** stop everything. An agent that has the token and a shell calls `/api/rpc` directly; a service it
creates can print its own variables to the log. To create infrastructure without seeing credentials, use the wizard
(`WizardCreate` generates the password and stores it encrypted) and the [rename](/en/guias/variaveis-e-secrets/#rename)
commands. If a password **was already shown** to an agent before this protection (a service created by older versions),
consider it exposed and change it.

## How to protect yourself

- **Paste the token only on machines that are yours.** The connection token is worth as much as the administrator's.
- **Ask for confirmation in the prompt.** Tell the agent to describe and wait before any destructive action (see the [connection](/en/agentes/conectar-claude-code/) prompt).
- **One server, one name.** With several servers, name each MCP and say which to use. The daemon already asks for confirmation before changing anything when more than one is registered.
- **Expose the API with TLS.** Set `[api].domain` so the API port terminates HTTPS.
- **Restrict the network.** If possible, leave port 9797 reachable only over a VPN or from known IPs.

## If the token leaks

1. Change `[api].token` in `config.toml`.
2. Restart the daemon. The `connection_token` rewrites itself.
3. Remove and register the MCP again on the legitimate machines.

## Master key and visitor key

By default the server has **a single key**, and whoever has it does everything. The prohibitions above apply on
**MCP**; `POST /api/rpc` with the same token ignored them, so an agent with a terminal could bypass them.

To close that, generate a **master key**:

```bash
sudo rustployd access-key --master      # writes [api].master_token and prints the master's connection token
sudo systemctl restart rustployd
```

- Generating the master is what **turns the protection on**. Without it, nothing changes.
- With the master, the key you already had (`[api].token`) becomes the **visitor** key: it is the one you hand to an
  agent (the **Conectar um agente** screen already copies that one). It goes through the rules on **every route**,
  `/mcp` and `/api/rpc`.
- You sign in to the GUI and the web UI with the **master's** connection token. Anyone who keeps the old key sees
  "forbidden" on the actions its level does not cover.
- The master **never leaves through the API**: `GET /api/access-key` and the agent login only deal with the visitor key.

What the visitor can do is `[api].visitor_level`:

| Level | What it does |
|---|---|
| `observer` | read-only: lists, state, logs, audit |
| `operator` (default) | operates what **already exists**: deploy, stop and restart, variables, secrets, domains, replicas, turning jobs on and off. It does **not** change what runs (source, image, command, volumes, compose) nor create or delete anything |
| `admin` | also creates and deletes projects, services, jobs, providers and Docker resources. Someone with `admin` can, at the limit, mount server folders into a container of their own: treat it as full access |

At any level the visitor still cannot reveal secrets, create a registry token, export with values, release audit
suspicions or resolve a `state_git` divergence, and **never sees** plaintext passwords (`GET /api/events`, which carries
them, is also refused).

<Aside type="note" title="Lost the master?">
  Edit `[api].master_token` in the server's `config.toml` and restart. Whoever administers the server always can.
</Aside>
