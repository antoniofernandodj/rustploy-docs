The **Runtime** screen (side menu) shows the container engine (Docker or Podman) of the **whole server**, not just what belongs to Rustploy. At the top, four
counters: **CONTAINERS**, **IMAGENS** (Images), **VOLUMES** and **NETWORKS**. Below, a sub-tab for each, plus the **Registry**.

| Sub-tab | Shows |
|---|---|
| **Containers** | all of them, running and stopped |
| **Images** | the images and whether they are in use |
| **Volumes** | Docker volumes (Rustploy only uses *bind mounts*, so these are not its own) |
| **Networks** | the networks, with the projects' ones identified |
| **Registry** | the built-in Docker registry |

Each list has the remove action. Docker **refuses** to remove what is in use. To clean up in one go, see
[Docker cleanup](/en/guias/limpeza-docker/).

## Registry

  src={registry}

  caption="The Registry sub-tab, with no repositories or tokens."
/>

The top reports the state: *"Registry ativo em 127.0.0.1:5100 · 0 repositório(s)"* (Registry active at 127.0.0.1:5100, 0 repositories). If
the registry is off, the screen warns you; turn it on under `[registry]` in
[`config.toml`](/en/instalacao/config-toml/#registry-optional).

| Element | What it does |
|---|---|
| The **REPOSITÓRIO / TAGS / TAMANHO / CRIADO / AÇÃO** table | the published repositories and their tags. Empty, it shows *"Faça `docker push` para o registry embutido."* (Do a `docker push` to the built-in registry.) |
| **Executar GC** (Run GC) | the *garbage collector*: removes manifests with no tag and blobs nobody uses |
| **Manter só as últimas tags de cada repositório** (keep only the latest tags) + **TAGS A MANTER** (tags to keep) | the [tag retention](#tag-retention): before every GC it deletes the oldest tags. Off by default |
| **TOKENS DE ACESSO (N)** (access tokens) | the `docker login` credentials |
| **+ Novo token** | creates a token |

Content is only created by `docker push`: the screen does not upload images.

### Tag retention

The GC only deletes what **no tag points to**, and a tag points forever. A CI that publishes one tag
per commit (`app/api:<sha>`) piles up one image per push, and the GC releases none of them. Retention
fixes that: when on, **before every GC** (the daily one and the one from the **Run GC** button) it
deletes, in each repository, the oldest tags and keeps the **N most recent**, counted by the date the
tag was published or moved. The manifest and layers left without a tag are freed from disk by the GC
right after.

- **Off by default.** Deleting data the owner did not ask to delete would be a surprise. Turn the
  switch on, pick **TAGS A MANTER** (tags to keep; minimum 1, default 10) and click **Save**.
- **It never deletes a tag a service uses.** If a Registry-source service points to `app/api:prod`,
  that tag stays even when it is the oldest, with or without push-to-deploy.
- **Tag only, never by digest.** An identical rebuild gives two tags the same digest; deleting by
  digest would take the one that still matters with it.
- The policy is stored in the infra `settings.yml`, so it goes through the
  [git sync](/en/guias/sincronizacao-git/).
- Through the agent: `RegistryRetentionSet{config:{enabled, keep_last}}`; reading comes in `RegistryStatus`.

### Push-to-deploy

A service whose source is an **image** from the registry itself (`127.0.0.1:5100/app/api:prod`, or the registry's
domain) can **redeploy by itself** on every push. In the service's **Advanced** tab, turn on
**Redeploy on every push to the embedded registry**. From then on the CI flow is just:

```bash
docker login registry.example.com          # token with push scope
docker build -t registry.example.com/app/api:prod .
docker push registry.example.com/app/api:prod   # Rustploy redeploys the service
```

No HTTP webhook and no Git on the server. The deploy fires when the **tag** changes: it matches the repository **and** the tag
of the service's image (no tag on the image means `latest`); a push by digest triggers nothing.

### Create a token

With no token at all, **no push or pull is authenticated**: create one before using the registry. Click **+ Novo token**.

<Shot
  src={novoToken}
  alt="The New token window with the Name field and the choice of scope between read-only (pull) and read and write (push)."
  caption="The New token window."
/>

| Field | |
|---|---|
| **NOME** (Name) | for example `ci-deploy` |
| **ESCOPO** (Scope) | **Somente leitura (pull)** (read-only) or **Leitura e escrita (push)** (read and write) |

Click **Criar token** (Create token).

<Shot
  src={tokenCriado}
  alt="The Token created window with the warning that the secret cannot be recovered and the docker login command with the secret blurred."
  caption="The docker login command, shown only once. (The secret was blurred in this image.)"
/>

<Aside type="danger" title="The secret appears once">
  The window shows the full **`docker login` command**, with the secret, and warns: *"O segredo não pode ser recuperado depois de fechar
  esta janela."* (The secret cannot be recovered after you close this window.) Click **Copiar** (Copy) before **Fechar** (Close). If you
  lose it, delete the token and create another.
</Aside>

The token appears in the **TOKENS DE ACESSO** table with **NOME**, **ESCOPO**, **CRIADO** (created) and **ÚLTIMO USO** (last used; `nunca`,
never, until the first time). The red **×** revokes it immediately.

Use a **push** token in CI and **pull** where you only download. The full flow, with a domain and HTTPS, is in
[Built-in registry](/en/guias/registry/).
