**Schedules** (side menu) lists *run-once docker-compose tasks, scheduled or manual, from all projects*. The same jobs of a project
appear on its **Jobs** tab. What a job is and how it works is in [Jobs and scheduled tasks](/en/guias/jobs/).

## The list

<Shot
  src={schedules}
  alt="The Schedules screen with an empty jobs table and the first step of the New job window, which asks you to choose the project."
  caption="Schedules, with no jobs, and the New job window open on the project choice."
/>

At the top, the **JOBS** counter and the **+ New job** button. The table's columns:

| Column | Shows |
|---|---|
| **NAME** | the job's name |
| **PROJECT / TRIGGER** | the project and the trigger service (or *standalone*) |
| **LAST RUN** | when it last ran |
| **RECURRENCE** | the schedule |
| **NEXT RUN** | the next firing, **in your time zone** |
| **WARM-UP** (Warming) | `quente` (warm), `frio` (cold) or `aquecendo…` (warming…) (see [Warm a job](/en/guias/jobs/#warm-a-job)) |
| **ACTIONS** | the **⋯** panel with *Rodar agora* (run now), *Cancel run*, *Aquecer*, *Reconstruir (sem cache)*, *View logs*, *Editar* and *Remover* |

With no jobs: *"No jobs registered yet."*

## Create a job

Click **+ New job**. The window has steps:

1. **CHOOSE THE PROJECT**. *"The job brings up its own docker-compose stack; the project defines the network."* Click **Select ›**.
2. **Trigger service**, or **None (standalone)**. The trigger only lends its environment variables.
3. **The form**, described below. The title shows *"NEW JOB — project / service"* (or *"none (standalone)"*).

### Compose source: Compose

<Shot
  src={compose}
  alt="The New job form with the Compose source, an example YAML with the busybox image, the main service field and the environment variables field."
  caption="The New job form, with the Compose source."
/>

| Field | What it is |
|---|---|
| **NAME** | for example `backup-db` |
| **COMPOSE SOURCE** | **Compose** (paste the YAML) or **Git** |
| **DOCKER-COMPOSE.YML** | the YAML. The screen brings a minimal example with `busybox` |
| **MAIN SERVICE** | the **name of the service inside the compose above** whose exit code decides whether the job succeeded |
| **VARIABLES AND SECRETS** | when **editing**, the **🔑 Variables and secrets** button opens the panel (see [A job's variables and secrets](#a-jobs-variables-and-secrets)); when **creating**, the panel shows up in the next step, right after **Create job**, because a job's secrets need its id. The job's variables win over the project's and the trigger service's |

### Compose source: Git

<Shot
  src={git}
  alt="The New job form with the Git source: account, repository and branch selectors, and the compose path in the repository."
  caption="The New job form, with the Git source."
/>

*"Select the connected account, the repository and the branch. The repo must already have a docker-compose.yml at the given path."* Choose the **GIT ACCOUNT**
(Git account), the **REPOSITORY** and the **BRANCH**, and check the **COMPOSE PATH IN THE REPO** (compose path in the repo; default
`docker-compose.yml`). With no accounts, connect one in [Settings → Git](/en/interface/configuracoes/#git). The job **clones the repository on
every run**.

### Recurrence

<Shot
  src={recorrencia}
  alt="The end of the New job form with the recurrence Manual, Intervalo, Diária or Semanal and the Voltar and Criar job buttons."
  caption="The end of the form: the recurrence."
/>

| Option | Fields |
|---|---|
| **Manual** | none: it only runs when you tell it to |
| **Interval** | every N hours |
| **Daily** | a time |
| **Weekly** | a weekday and a time |

<Aside type="caution" title="The time is in UTC">
  The time you enter is **UTC**. The **NEXT RUN** column shows it in your time zone: use it to check.
</Aside>

Click **Create job**. **‹ Back** goes back to the previous step.

## A job's ⋯ menu

<Shot
  src={jobsMenu}
  alt="A job's actions panel open over a project's job list, with the job name, the warm state and the Rodar agora, Aquecer, Ver logs, Pausar, Editar and Remover actions."
  caption="The panel from the ⋯ button (the job and project names are blurred)."
/>

The **⋯** button at the end of the row opens a panel with the job name, the warm-up state (*quente*,
"warm", and *aquecido em*, "warmed at", with date and time) and the actions:

| Action | Effect |
|---|---|
| **▶ Run now** | runs right away, outside the schedule. With a run in progress, it becomes **■ Cancel run** |
| **◐ Warm** | pulls the images and builds the build cache **without running** the job |
| **↻ Rebuild (no cache)** | shown with the job **warm**: rebuilds from scratch and pulls the images again. See [Rebuild from scratch](/en/guias/jobs/#rebuild-from-scratch) |
| **≡ View logs** | the output (stdout and stderr) of the runs |
| **‖ Pause** | suspends the schedule. With the job paused, the button becomes **Enable** |
| **🔑 Variables and secrets** | opens the screen with the job's environment variables and secrets. See [A job's variables and secrets](#a-jobs-variables-and-secrets) |
| **✎ Edit** | opens the job to change it |
| **✕ Remove** | deletes the job, after **asking for confirmation**. It cannot be recovered |

**Remove** and **Rebuild** close the panel and open a confirmation dialog. **Cancel**
(Cancel) changes nothing (the job stays in the list); **Remove** deletes the job.

## A job's variables and secrets

The **🔑 Variables and secrets** action in the ⋯ menu opens a screen with the job's environment variables
and the **job's secrets**, with the same buttons as a service's *Environment* tab and the project's variables:

| Button | Effect |
|---|---|
| **✕** | removes the variable (or the secret) |
| **✏️** / **✎** | renames the key (the value stays) / edits the value in place |
| **🔒** | moves the variable to a **secret**: the value is stored encrypted (`ENC[age:…]`) |
| **🔓** | turns the secret back into a plain variable |
| **↑** | moves it up to the project: the project's services and jobs inherit it |
| **👁 / 🙈 / 📋** | shows, hides and copies a secret's value (the access is logged in the server audit) |
| **.env** | edits all variables as `KEY=VALUE` text |

At run time a job secret wins over the trigger service's secret, which wins over the project's.
**Every operation that changes or exposes a variable asks for confirmation**; only reordering doesn't.
This also applies to project and service variables.

## After creating

- If the job uses large images or a build, use **Warm** before the first run.
- To run the job **before every deploy**, add it to the service's pre-deploy queue: see
  [Domains, healthcheck and advanced options](/en/interface/servico-configuracao/#the-pre-deploy-queue).
