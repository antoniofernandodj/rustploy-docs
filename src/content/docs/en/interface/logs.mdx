Logs open in a **window of their own**, isolated from the rest of the app: that way a service that writes a lot does not freeze the
interface. The window is the same for both kinds of log.

## Runtime logs

<Shot
  src={runtime}
  alt="The backend service's Logs window with the container's live log lines. The user and tenant identifiers were blurred."
  caption="The runtime log window. The identifiers were blurred in this image."
/>

It is the output (stdout and stderr) of the **running container**. To open it:

- on the service screen, the **Logs → Abrir logs em janela** (Open logs in a window) tab; or
- the **Logs de runtime** button in the side panel.

The title is `Logs · service-name`. At the top, the counter (*"15 linhas · ao vivo"*, 15 lines, live) and three buttons:

| Button | Effect |
|---|---|
| **↑** | goes to the **top** |
| **↓** | goes to the **bottom** |
| **Copiar tudo** (Copy all) | copies all the content |

When it opens, the window shows the last lines already emitted (the *tail*) and **keeps appending** new ones in real time. The text is
**selectable**, so you can copy a snippet with the mouse. Each line starts with a time (`HH:MM:SS`) that Rustploy adds, followed by the
line as the container emitted it (here, already carrying the app's own timestamp).

With no output, the window says *"(sem logs ainda — aguardando o serviço emitir saída)"* (no logs yet, waiting for the service to emit output).

## Build logs

<Shot
  src={build}
  alt="A deploy's Build logs window showing the docker build steps, from Step 1 to Step 7, with the cache-use indication."
  caption="A deploy's build log window."
/>

It is the output of a deploy's **build** (the `docker build` steps, the clone, the pull). To open it, go to **Deployments** on the service
screen and click **≡** on the deploy's row. The title is `Build logs · dep_…`, with the deploy's id.

A deploy still in progress shows the build **live**. One that failed carries, at the end, the line `==> Erro em [State]: …` with the
**cause**. See [Where the cause of a failure is](/en/conceitos/ciclo-de-vida/#where-the-cause-is).

## What is stored

The **build log** is stored in the database and can be opened later. The **runtime log** is stored too, in files on the
server (see below), and survives the container swap on a deploy.

### Stored runtime log

<Aside type="note">Available from daemon 0.1.34 (release v0.1.40). Before that, the runtime log was live-only.</Aside>

The daemon records each container's log while it runs and, **before removing a container** (the deploy swap and the
rollback of a failed deploy), saves what had not been recorded yet. So you can see "what happened before the last
deploy" and the cause of a new container that crashed within seconds.

- When the window opens, the lines come from the stored log (the 500 most recent) and new ones keep arriving live.
- **Carregar anteriores** (Load earlier, the button on top) brings the older page of log, above. Where the container
  changed between two lines, the separator *"— other container: …"* appears.
- Retention: **14 days** and **50 MiB per service** (the oldest goes first), adjustable in the
  [`[logs]`](/en/instalacao/config-toml/) section of `config.toml`. Deleting the service deletes its log.
- **Compose** services remain live-only.

<Aside type="caution" title="The log may contain secrets">
  If the application prints a password, it is in the log, live and now also on disk (`0700` folder, `0600`
  files). Avoid logging secrets and, if you need longer retention or search, ship the logs off the server (for
  example with a template such as Loki or Grafana from the [catalog](/en/templates/)).
</Aside>

An agent reads the history with the `LogsHistory` command.

The window keeps at most **6,000 lines** on screen: past that, it discards the oldest and keeps the 4,000 most recent.

The logs of a [job](/en/interface/schedules/) run open in the same window, through the job's **Ver logs** action.
