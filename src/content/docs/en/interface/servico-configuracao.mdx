These are tabs of the [service screen](/en/interface/servico/). After changing any of them, **run a new Deploy** for the change to
take effect in the container.

## Domains

<Shot
  src={dominios}
  alt="The Domains tab with no domains, with the fields to add a domain, the container port, the HTTPS/TLS switch and the host TCP port section."
  caption="The Domains tab of a service with no domain."
/>

**DOMAINS (N)** lists the service's routes. The screen text reminds you: *"Each domain can point to a different container port."*

To **add** one:

1. Under **ADD DOMAIN**, type the name (`app.example.com`).
2. Under **CONTAINER PORT (optional)**, give the port of the app that receives this domain. Blank means the **service's default**.
3. Turn on **HTTPS / TLS** for an automatic certificate.
4. Click **Add domain**.

DNS must already point at the server, and ACME must be on for HTTPS: see [Domains and automatic HTTPS](/en/guias/dominios-e-tls/).

### Host TCP ports

The **HOST TCP PORTS** block is for when the service is **not HTTP** (a database, a broker, a storage API): each
port opens a TCP port on the **server** that forwards straight to a container port, without going through domain
routing. A service can have up to 8.

| Field or button | Effect |
|---|---|
| **Host port** | the number on the server. Empty = automatic: Rustploy picks a free one from the range (default 20000–20999) and opens it in the firewall. The firewall helper only opens ports in the `[external_ports]` range |
| **Container port** | where the port leads. Empty = the service's default port |
| **Suggest container ports** | lists the ports the service probably has (what the container listens on, what the image and the compose file declare, and a per-product table); clicking one fills in the container port and the label |
| **Label** | optional, only names the port on screen ("console", "dashboard") |
| **Add port** | saves. A host port that already exists is edited instead of repeated |
| **✕** | removes the port and closes it in the firewall (if no other service uses it) |

The port that leads to the service's default port appears on the **Connection** tab, under **Host port** and
**External URL**. This makes the service reachable from the **internet**: use a strong password. See
[Server security](/en/operacao/seguranca-do-servidor/#the-firewall-helper).

## Healthcheck

<Shot
  src={healthcheck}
  alt="The Healthcheck tab with the None, Tcp, Http and Docker types, and the interval, timeout, retries and start period fields."
  caption="The Healthcheck tab, with the Tcp type selected."
/>

Choose the type under **KIND**: **None**, **Tcp**, **Http** or **Docker**. With **Http**, the path and the expected status also appear.

| Field | Screen default | Meaning |
|---|---|---|
| **INTERVAL (s)** | 5 | pause between attempts |
| **TIMEOUT (s)** | 3 | how long each attempt may take |
| **RETRIES** | 10 | maximum attempts |
| **START PERIOD (s)** | 5 | wait before the first one |

Click **Save**. What each type means and how to choose is in [Healthcheck](/en/guias/healthcheck/). A new service starts with **None**:
configure one before using it in production.

Click **Save**.

### Links: the services this one uses

**USES (N)** lists the services this one **uses**: the database, the S3, the queue, the cache. Each
link does two things:

- **Order:** this service waits for the other to come up, on a deploy with dependencies and on daemon
  boot, without repeating the other under **Depends on**.
- **Variables:** on the next deploy, this service receives `<PREFIX>_HOST`, `<PREFIX>_PORT` and
  `<PREFIX>_URL` from the other. The default prefix is the other's name in uppercase (`db` →
  `DB_HOST`); you can pick another one in **Variable prefix**. The `_URL` is the same as in the
  Connection tab: for a database, with user and password; for an S3 or an app, `http://host:port`.

Variables you typed in the project or the service **always win** over the ones the link hands over.
So you can adopt links without touching what already works, and delete the manual variables over time.

From **another project**, you can only link to a [shared database](/en/guias/banco-compartilhado/), and
Rustploy grants the project access to it by itself. The shared database screen shows **Accepts links
from other projects**: off, it refuses new links (the existing ones keep working).

**USED BY (N)** is the same information seen from the other side: on the `db` screen, `api` shows up.
Adding or removing there writes to the service that uses it. Removing a link, on either side, asks
for confirmation.

<Aside type="note">
In a **Compose** service, the variables go to the stack's `.env`, like any variable: they only reach
the container if the YAML uses them (`environment: [DATABASE_URL=${DB_URL}]`). Jobs that have this service
as their trigger (including the ones in the pre-deploy queue) also receive the links' variables.
</Aside>

#### Resource: the bucket or database the link creates

When you pick the service in **Link to**, the field that fits it appears:

- on an **S3** (RustFS, MinIO), the **Bucket (optional)** field: this service also receives `<PREFIX>_BUCKET`.
  With **Public read** on, anyone can read the files (to serve images, for example);
- on a **Postgres, MySQL or MariaDB**, the **Database (optional)** field: this service receives
  `<PREFIX>_DATABASE`, and `<PREFIX>_URL` points to it;
- on the others (cache, queue, application), none: the link only hands over the address.

Rustploy creates the resource on **this service's next deploy**, before the pre-deploy queue (a migration
already finds the database), and only if it does not exist yet: the deploy log says "created" or "already
existed". The other service must be online; a deploy with dependencies takes care of that. If it cannot be
created within 60 seconds, the deploy stops with the cause in the log, without touching what is online.

Removing the link **does not delete** the bucket or the database. Resources only work for services in the same
project; for a shared database in another project, use a [managed database](/en/guias/banco-compartilhado/).

### The pre-deploy queue

<Shot
  src={fila}
  alt="The end of the Advanced tab with the empty pre-deploy queue, the job selector and the Add to the queue button."
  caption="The pre-deploy queue, empty."
/>

**PRE-DEPLOY QUEUE (N)** runs [jobs](/en/interface/schedules/) **in order** before each deploy, *"manual or webhook, one at a time. If any one's
exit code is different from 0, the queue stops and the deploy does not happen, and the following checks do not run."* With none, the
screen says *"No check configured — the deploy goes straight through."*

1. First create the job in **Schedules**.
2. Under **ADD TO THE QUEUE**, pick the job (*"choose job…"*).
3. Click **Add to the queue**.
4. To **reorder**, drag by each row's **⋮** handle.

The typical case is running the database migration before swapping the version. Details in [Pre-deploy checks](/en/guias/pre-deploy/).
