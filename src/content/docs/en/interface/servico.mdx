In **Projects → (project) → Services**, a card's **Open ›** button takes you to the service screen. This is where you
deploy and configure everything.

## The header

At the top: **‹ project-name** (back to the project), the **service name** and, just below, the **status** (`Stopped`,
`Running`, `Deploying`, `Degraded`, `Error`…). On the right are the actions. In the desktop app, **Deploy** is a split
button: clicking **Deploy** deploys, and the **▾** arrow attached to it opens the other actions (Reload, Rebuild, Warm,
when the service allows it, and Export service). **Stop** stays apart, in red. While an action is running, its item is
disabled in the menu.

| Button | What it does |
|---|---|
| **Deploy** | starts a deploy of the service (it joins the [queue](/en/guias/fila-de-deploys/)). With dependencies it first shows the order in a modal: Confirm, Only the service or Reject ([details](/en/guias/dependencias-e-religar/)) |
| **Reload** | **restarts** the container that is running, with no redeploy. It does not apply new variables |
| **Rebuild** | today does **exactly the same as Deploy** |
| **Stop** | stops the service. It asks for confirmation: traffic stays interrupted until a new deploy |
| **Export service** | generates a file to recreate the service on another server |

<Aside type="note" title="Rebuild and Deploy">
  In the desktop app, **Rebuild** calls the same function as **Deploy**: deploying a Git or zip service already rebuilds the
  image. Use **Deploy**.
</Aside>

To go back a version, use **Roll back to this** on the [Deployments](#deployments) tab: every deploy that went
live became a **release** (v1, v2, v3…), and rolling back to it brings back that moment's image and configuration.

## The side panel

Two panels sit on the right:

| Panel | Shows |
|---|---|
| **STATUS / UPTIME / SERVICES** | the service's status and two **global** numbers |
| **LOGS** | the button to open the runtime logs in a window |

<Aside type="caution" title="UPTIME and SERVICES are the server's, not the service's">
  **UPTIME** is how long the **daemon** has been up, and **SERVICES** is the count of running services out of the total (`0/7`),
  across all projects. Neither describes the open service. Only the **STATUS** is its own.
</Aside>

## The tabs

The tabs depend on the service type. An **Application** service has **General**, **Connection**, **Environment**, **Domains**,
**Deployments**, **Healthcheck**, **Logs** and **Advanced**. Every service also has a **Data** tab (take the data to a file and bring it back: see
[Export and import a service's data](/en/guias/dados-do-servico/); and the **Backup to S3**, manual or scheduled: [Data backup to S3](/en/guias/backup-no-s3/)). A database or **Compose** stack also gets **Migrate** (Migrate: move the
data to a [shared server](/en/guias/migrar-banco/)). A shared database server has the **Databases** tab.

This page covers **General**, **Connection**, **Environment**, **Deployments**, **Logs**, **Migrate** and **Databases**. **Domains**, **Healthcheck** and **Advanced** are in
[Domains, healthcheck and advanced options](/en/interface/servico-configuracao/).

### General

The service name is edited right in the header **title**: click, type, and it saves half a second
after the last keystroke (there is no Rename button). The effect of the new name **varies by type**
(in the web UI, the warning shows when you hover over the title):

- **Compose:** *"The Docker stack and volumes do not change with the name: the data stays the same."*
- **Application:** *"The internal hostname (`rp_<name>`) only applies on the next deploy. Other services that use the old name in environment variables need to be updated."*

#### An Application service

<Shot
  src={git}
  alt="The General tab of an Application service, with the name editable in the title, the choice of Git, Registry or Zip provider, the repository URL or image field, branch, port, username and credentials."
  caption="General of an Application service, with no source configured yet."

A service just created by the wizard starts **empty**: this is where you set the source.

| Field | What it is |
|---|---|
| **PROVIDER** | **Git** (a plain URL), **Registry** (pick the repository and the tag in two selects, among the images already published to the server's [embedded registry](/en/interface/docker-e-registry/); the image is stored as `127.0.0.1:<port>/repo:tag`) or **Zip** (upload: the app sends the file straight from disk, with a **progress bar** and a **Cancel** button). With an account connected in [Settings → Git](/en/interface/configuracoes/#git), the account's tab also appears |
| **SOURCE — REPOSITORY URL / IMAGE** | the repository URL **or** the registry image, in the same field |
| **BRANCH** | the branch (default `main`) |
| **PORT** | the app's port **inside** the container |
| **USERNAME** | the clone user, only if the provider requires it |
| **CREDENTIALS (secret)** | the **name** of a project secret holding the clone token |

The text under the main field gives the rule: *"A repository URL becomes Git; otherwise it is a registry image."* That is, `github.com/user/repo` is cloned and built, and `nginx:latest` is pulled.
Scroll the tab to see the other fields (**Dockerfile**, build context and more). The details and the fields that do not have an effect
yet are in [Deploy from a Git repository](/en/guias/git/).

Values ready to copy:

| Row | Means |
|---|---|
| **Container port** | the app's port inside the container |
| **Host port** | the TCP port opened on the server, if any (see [Domains](/en/interface/servico-configuracao/#host-tcp-ports)) |
| **Domain** | the configured domain |
| **TLS** | `disabled` or on |
| **External URL** | the URL from **outside** the server, when there is an external port |
| **Internal URL** | the URL **inside the project network**, such as `http://rp_api:80`. It is the one other services in the project use |

Below, **CONTAINERS (N)** lists the service's running containers. For databases, the **Internal URL** is the connection
string you put in `DATABASE_URL`.

### Deployments

<Shot
  src={deployments}
  alt="The Deployments tab with the deploy webhook block explaining that the token is born on the first deploy, and an empty deploy list."
  caption="The Deployments tab of a service that has not had a deploy yet."
/>

Two blocks:

**DEPLOY WEBHOOK**. *"The token is born on this service's first deploy, so run a deploy for the URL to appear. A POST to this URL triggers a deploy. The body is ignored: the token in the URL itself is the authentication. Regenerating invalidates the previous URL."* After the first deploy the URL appears
here, with **Copy** and **Regenerate**. See [Deploy webhooks](/en/guias/webhooks/). Compose services have no webhook.

**The deploy list**, with each one's **id**, **duration**, **start** and **image**. Every deploy that went live
(**Live**) gets the badge of its **release** (**v1**, **v2**…), and the one live right now also shows **current**.
On each row:

| Button | Effect |
|---|---|
| **≡** | opens the deploy's **build log** in a window |
| **Compare** | shows what would change if you rolled back to this release (releases only) |
| **Roll back to this** | rolls the service back to this release, after confirming (releases that are not the current one) |
| **✕** | removes the deploy's record (only those that have already finished) |

#### Releases: compare and roll back

A **release** keeps what ran in that deploy: the image, pinned by its id or digest (not by the tag, which can
change later), and a copy of the service configuration (variables, ports, command, replicas, healthcheck,
domains, links) and of the project variables.

**Compare** opens the list of what changes going from the **current** configuration to the release's, split
into image, service configuration, service variables and project variables. A secret shows as `secret:NAME`,
never its value.

**Roll back to this** asks for confirmation and then:

1. replaces the service configuration with the release's (the name and the project stay as they are now);
2. deploys the release's image, **without a build**: the log says *"Voltando para a v9"*;
3. once live, the deploy becomes a new release (for example **v13**), marked *"restores v9"*.

What is **not** rolled back:

- **the project variables**, which apply to every service in the project. Compare shows which ones changed,
  so you can decide;
- **secret values**: the rollback uses each secret's current value;
- **the images inside a Compose stack**: rolling back reruns `compose up` with that release's content, but the
  tags in the file point to whatever exists now.

The Docker cleanup spares the images of each service's **3 newest releases**. An older release whose image was
deleted shows *"This release's image was deleted"*: you can compare it, but not roll back to it. A registry
image pinned by digest rolls back even if it was deleted here, because it is pulled again.

Empty, it shows *"No deploy yet."* The cause of a failed deploy is in the build log: see
[The lifecycle of a deploy](/en/conceitos/ciclo-de-vida/#where-the-cause-is).

### Logs

The **Execution logs** button opens the container's **runtime logs** in a window of their own, isolated
from the rest of the app, so the interface does not freeze under heavy volume. The same shortcut exists in the **LOGS** side panel
(**Runtime logs**). The build log opens from the **Deployments** tab. Both windows are in [Log windows](/en/interface/logs/).

The runtime log is read from Docker **live** and **is not stored**: when a deploy swaps the container, the old log goes with it.

### Migrar (Migrate)

<Shot
  src={migrar}
  alt="The Migrate tab of a database service, with the source database, destination, env var to replace fields and the Migrate and Refresh buttons."
  caption="The Migrate tab of a database running inside a project."
/>

The tab exists on **databases and Compose stacks**. It moves the data of a database that lives **inside this
database** to a database on a [shared server](/en/guias/banco-compartilhado/).

<Aside type="caution" title="The migration stops the services">
  The services that use this database are **down** during the copy. First create the destination
  database on the shared server (in its **Databases** tab), ticking **"Do not touch env vars"**. The destination must have the **same engine** and belong to the **same project**.
</Aside>

| Field | What it is |
|---|---|
| **SOURCE DATABASE** | the name of the database **inside this database server** (for example, the project name) |
| **DESTINATION** | the database created on the shared server, chosen from a list |
| **ENV VAR TO REPLACE** | the variable with the connection string. Blank means `DATABASE_URL` or `MONGODB_URI` |

**Migrate** starts the process, which runs in the background and shows progress. **Refresh** re-reads the
state, and is how you pick it up again after leaving the screen. For the step by step, what the migration does,
how to roll back and how to discard the old database, see [Migrate a database](/en/guias/migrar-banco/).

### Databases

<Shot
  src={dbLista}
  alt="The Databases tab of a shared database server, with the list of databases, each pointing to its consumer project and environment variable, and the start of the New database form."
  caption="The Databases tab of a shared server: the list and the New database form."
/>

The tab appears on a **shared database server**. In **DATABASES (N)**, each row is a database with its own
user, with **no access to the others**. It shows the database, the project that consumes it and the variable that
receives the connection string. The red **×** **deletes the database and the user, with the data**: there is no way
to recover it.

Clicking a database **name** opens the **URL** row with **Copy**: it puts the full connection string on the clipboard without displaying it.

<Shot
  src={dbNovo}
  alt="The New database form with the name, consumer project, env var, connection limit and query timeout fields, the two env var options and the Create database button."
  caption="The New database form."
/>

| Field | What it does |
|---|---|
| **name** | name of the database and the user: `a-z`, `0-9` and `_` |
| **consumer project** | the project that will use the database. It receives the connection string in a variable |
| **env var** | the variable that receives the URL. Default: `DATABASE_URL` or `MONGODB_URI` |
| **connection limit** | optional. Not valid on MongoDB |
| **timeout de query** | optional, in ms. Postgres only |
| **Overwrite the env var if the project already has it** | without it, creation is **refused** if the variable already exists |
| **Do not touch env vars (I will migrate the data first)** | creates the database without touching the application: the first step of a [migration](/en/guias/migrar-banco/) |

After **Create database**, redeploy the consumer project so the application reads the variable.
Everything about isolation, limits and conflicts is in [Shared database](/en/guias/banco-compartilhado/).
