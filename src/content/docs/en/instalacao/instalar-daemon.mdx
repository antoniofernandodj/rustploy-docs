The supported installation path is the `rustployd` **`.deb`** package, for Debian, Ubuntu and
derivatives. It creates the `rustploy` user, installs the systemd service and starts the daemon.

## In one command

On the VPS, as root:

```bash
curl -fsSL https://raw.githubusercontent.com/antoniofernandodj/rustploy/main/install.sh | sudo sh
```

The installer downloads the `.deb` from the **latest GitHub release**, checks the SHA-256, installs it, generates a
token, starts the service and prints the **connection token**. To allow access from outside the VPS, add `--remote`
after `sh -s --`. All the details, the options and how to read the script before running it are in
[Quick install](/en/instalacao/instalacao-rapida/).

<Aside type="note" title="Prefer to build it, or no access to GitHub?">
  Use one of the paths below: `cargo install rustploy` (the binary only) or the `.deb` built from the repository
  (which creates the user, the service and the firewall helper).
</Aside>

## Choosing the container engine: Docker or Podman

Rustploy does not run containers itself: it uses a **container engine**, the program that actually creates and
runs each service. You choose with `--engine`, and **with either one the installer installs the engine if it is
missing**:

| | `--engine docker` (default) | `--engine podman` |
|---|---|---|
| Command | `… \| sudo sh` | `… \| sudo sh -s -- --engine podman` |
| What it installs | Docker Engine (`docker-ce`) from Docker's official repository | Podman (4.7 or newer) and a `compose` provider |
| RAM while idle | `dockerd` + `containerd` always run (~100 to 150 MB) | **no daemon**: Podman only wakes up when rustploy calls it |
| Systems | Debian 12+, Ubuntu 22.04+ | Debian 13+, Ubuntu 24.04+ (`podman compose` only exists from 4.7) |

<Tabs>
  <TabItem label="Docker (default)">
    ```bash
    curl -fsSL https://raw.githubusercontent.com/antoniofernandodj/rustploy/main/install.sh | sudo sh
    # same as: … | sudo sh -s -- --engine docker
    ```

    If `docker` is already on the machine, the installer **leaves it alone**. If not, it follows
    [Docker's official guide](https://docs.docker.com/engine/install/ubuntu/): removes conflicting packages (only
    the installed ones: `docker.io`, `podman-docker`, `containerd`, `runc`…), adds Docker's apt repository (GPG key
    + `/etc/apt/sources.list.d/docker.sources`), installs
    `docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin` and enables the `docker`
    service. On Debian it uses Docker's `debian` repository; on derivatives (Mint etc.) it uses the base Ubuntu/Debian
    codename. On a distribution it does not recognise, it falls back to the distribution's own `docker.io`.

    **By hand** (Ubuntu; on Debian replace `ubuntu` with `debian`):

    ```bash
    # 1. remove conflicting packages (skip if none are installed)
    sudo apt remove $(dpkg --get-selections docker.io docker-compose docker-compose-v2 \
      docker-doc docker-buildx podman-docker containerd runc | cut -f1)

    # 2. Docker's apt repository
    sudo apt update
    sudo apt install ca-certificates curl
    sudo install -m 0755 -d /etc/apt/keyrings
    sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
    sudo chmod a+r /etc/apt/keyrings/docker.asc
    sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
    Types: deb
    URIs: https://download.docker.com/linux/ubuntu
    Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
    Components: stable
    Architectures: $(dpkg --print-architecture)
    Signed-By: /etc/apt/keyrings/docker.asc
    EOF
    sudo apt update

    # 3. install and check
    sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
    sudo systemctl status docker
    ```

    Then install rustploy as usual (the `.deb` accepts `docker-ce` as its dependency).
  </TabItem>
  <TabItem label="Podman">
    ```bash
    curl -fsSL https://raw.githubusercontent.com/antoniofernandodj/rustploy/main/install.sh | sudo sh -s -- --engine podman
    ```

    The installer does four things, in this order:

    1. **Installs Podman** and a compose provider (`docker-compose-v2`, `docker-compose-plugin` or `docker-compose`,
       whichever exists first). This happens *before* the rustploy `.deb` so `apt` does not pull Docker in too (the
       package accepts `docker.io`, `docker-ce` **or** `podman` as its dependency).
    2. **Enables `podman.socket`**: systemd stands guard on `/run/podman/podman.sock` and wakes Podman only when
       rustploy knocks there. This is where the RAM saving comes from.
    3. **Gives the `rustploy` user access to that socket**, which is born `root:root`. A
       `/etc/systemd/system/podman.socket.d/rustploy.conf` file with `SocketGroup=rustploy` makes that permanent (a
       hand-made `chgrp` is lost when the socket is recreated).
    4. **Points rustploy at Podman**: a `/etc/systemd/system/rustployd.service.d/podman.conf` file adds
       `podman.socket` to its dependencies (the package unit only orders itself after `docker.service`, without pulling it in), and `[docker] socket_path` in `config.toml` becomes
       `/run/podman/podman.sock`. (The section is still called `[docker]` for compatibility.)

    **By hand:**

    ```bash
    sudo apt install podman docker-compose-v2     # or docker-compose-plugin / docker-compose
    sudo mkdir -p /etc/systemd/system/podman.socket.d /etc/systemd/system/rustployd.service.d
    printf '[Socket]\nSocketGroup=rustploy\nSocketMode=0660\n' | sudo tee /etc/systemd/system/podman.socket.d/rustploy.conf
    printf '[Unit]\nAfter=podman.socket\nWants=podman.socket\n[Service]\nEnvironment=RUSTPLOY_CONTAINER_ENGINE=podman\n' \
      | sudo tee /etc/systemd/system/rustployd.service.d/podman.conf
    sudo sed -i 's|^socket_path *=.*|socket_path = "/run/podman/podman.sock"|' /etc/rustploy/config.toml
    sudo systemctl daemon-reload
    sudo systemctl enable --now podman.socket
    sudo systemctl restart podman.socket rustployd
    ```
  </TabItem>
</Tabs>

<Aside type="caution" title="Switching engines does not move what is already running">
  Docker containers, images and volumes are **not** migrated to Podman (or the other way round): the new engine
  starts empty. After switching, redeploy every service; databases need care because their data lives in volumes
  of the old engine. To actually free Docker's RAM, once everything is migrated:
  `sudo systemctl disable --now docker docker.socket`. Podman is supported in **rootful** mode only (via the
  socket in `/run/podman/`).
</Aside>

## What the package installs

| Item | Where |
|---|---|
| Daemon | `/usr/bin/rustployd` |
| Firewall helper (root) | `/usr/libexec/rustployd-fw` |
| Configuration | `/etc/rustploy/config.toml` |
| systemd services | `rustployd.service`, `rustployd-fw.socket`, `rustployd-fw.service` |
| Database and data | `/var/lib/rustploy` |

The package depends on `docker.io`, `docker-ce` **or** `podman`. The service runs as the `rustploy` system user,
which joins the `docker` group. See
[Choosing the container engine](#choosing-the-container-engine-docker-or-podman).

## From crates.io

If you prefer to compile on the machine itself, the daemon's crate is called `rustploy` (the installed
binary is `rustployd`):

```bash
cargo install rustploy
```

This only installs the binaries in `~/.cargo/bin`. It does not create the user, the systemd service or
`config.toml`: for a production server, prefer the `.deb` below.

## Build the package

On a machine with the Rust toolchain and `cargo-deb`:

```bash
git clone --recurse-submodules https://github.com/antoniofernandodj/rustploy.git
cd rustploy
cargo install cargo-deb
make deb-rustploy
# produces rustploy-daemon/target/debian/rustployd_<version>_<arch>.deb
```

Copy the `.deb` to the server and install it:

```bash
sudo dpkg -i rustployd_*.deb
sudo apt-get install -f     # only if a dependency is missing
```

## Check

```bash
systemctl status rustployd
journalctl -u rustployd -f
```

By default the API listens on `127.0.0.1:9797`, **with no token**. That is fine for testing on the VPS
itself, but it does not yet let any remote client in.

## Enable remote access

<Aside type="tip" title="Already ran the one-line command?">
  The installer already generated the token and wrote `[api]` to `config.toml`. With `--remote`, the API already
  listens on `0.0.0.0:9797`: skip to step 4 (get the token) and 5 (firewall). Without `--remote`, run the command
  again with the option.
</Aside>

<Steps>
1. Generate a strong token:

   ```bash
   openssl rand -hex 32
   ```

2. Edit `/etc/rustploy/config.toml` and open the `[api]` section:

   ```toml
   [api]
   bind_address = "0.0.0.0"
   port         = 9797
   token        = "<the token you generated>"
   ```

   The daemon refuses to start with a public `bind_address` and no `token`.

3. Restart:

   ```bash
   sudo systemctl restart rustployd
   ```

4. Get the [connection token](/en/instalacao/primeiro-acesso/):

   ```bash
   sudo rustployd access-key
   ```

5. Open port 9797 in the provider's firewall and, if you use `ufw`, in `ufw`.
</Steps>

<Aside type="caution">
  If `config.toml` has an error, the daemon **silently ignores it** and starts with the defaults. If
  step 4 says there is no token, the file was not read. See
  [The config.toml file](/en/instalacao/config-toml/#check-what-the-daemon-read).
</Aside>

<Aside type="caution">
  Without `[api].domain`, port 9797 speaks **plain HTTP** and the token travels unencrypted. For real
  use, configure a domain (see below) or close the port to the internet and reach it over a VPN or an
  SSH tunnel.
</Aside>

## Turn on HTTPS

Point your domains' DNS at the server and turn on ACME:

```toml
[ingress.acme]
enabled = true
email   = "you@example.com"
```

For the dashboard to use HTTPS too, set the API domain:

```toml
[api]
domain = "rustploy.mysite.com"
```

Restart the daemon. The full reference is in [The config.toml file](/en/instalacao/config-toml/).
