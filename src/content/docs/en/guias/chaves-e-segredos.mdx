A Rustploy server has a few files and fields with "key" in the name. **Only two groups protect your secrets**;
the rest is something else.

## The map

| Name | Where | Secret? | Role |
|---|---|---|---|
| **The server's `age` identity** | `age_identity` under `[secrets]` in `config.toml` **or** the file at `age_key_path` (default `/etc/rustploy/age.key`) | **yes** | The real key. Encrypts and decrypts every secret (`ENC[age:…]`). The daemon creates it on its own on first boot. |
| **`recovery_recipient`** | `config.toml`, under `[secrets]` | no (public, `age1…`) | The extra lock: every secret **saved afterwards** is readable by the server **and** by your recovery key. |
| **The recovery private key** | **off the server**, in your vault | **yes** | The only one that opens the secrets if you lose the server. It is born together with the public one. |

## How they fit together

- A new secret is stored as `ENC[age:…]`, which opens only with the server's identity **or** with the recovery key.
- The `config.toml` `age_identity` and `age.key` are **the same thing in two places**. The daemon reads the `config.toml` one first and, if absent, the file. **One** is enough.
- The state files (and the [git sync](/en/guias/sincronizacao-git/) repository) only contain ciphertext. That is why versioning them is safe, **as long as the keys do not go along**.
- If the daemon finds no identity and `ENC[age:…]` secrets already exist, it **refuses to start**. That is on purpose: generating a new one would leave the secrets unreadable.

<Aside type="danger" title="Do not swap the identity for another one">
  If you put a **different** key in `age_identity` than the one that encrypted the secrets, the daemon starts using the
  new one and the existing secrets become unreadable, **with no warning**. To move the identity from `age.key` to
  `config.toml`, copy the **same** value and check they are equal before deleting the file.
</Aside>

The recovery key is also what lets you [recover a whole server](/en/guias/recuperar-servidor/) and it is **required** by
[data backup to S3](/en/guias/backup-no-s3/), which is always encrypted.

## Generate the recovery key from the interface

In the desktop app and the web UI: **Settings → Chave de recuperação (Recovery key) → Generate and download**.

1. The server generates the key pair, writes **only the public key** to `[secrets] recovery_recipient` (in `config.toml`,
   no restart) and **re-encrypts the secrets that already exist**, so the new key opens the old ones too.
2. The private key is shown **only once** and the client downloads the file
   `rustploy-recovery-key-<server>-<YYYYMMDD>.txt` (the desktop app writes it to *Downloads* without overwriting; the web
   UI uses the browser download).
3. **Move the file to a vault, off the server.** The server does not keep the private key: that file is the only copy.

Already have a key? The screen asks you to confirm the replacement. Replacing **deletes nothing**: old backups and commits
keep opening **only with the old key**, so keep both. The AI agent (MCP) cannot generate this key, on purpose.

The "no recovery key" warnings in the **Backups** and **Sync** tabs have a **Generate recovery key** button that takes you
to the same place.

## Set up the recovery key by hand

If you prefer, do this once, **on your own machine** (not on the server):

```bash
rustploy-cli keygen
```

The output has two parts:

```text
# chave pública: age1xxxxxxxx…
AGE-SECRET-KEY-1XXXXXXXX…
```

1. Keep the `AGE-SECRET-KEY-1…` line in a **vault, off the server**. It never goes to the server.
2. On the server, copy `config.toml`, put **only the public one** under `[secrets]`, and validate before restarting:

```bash
sudo cp -a /etc/rustploy/config.toml /etc/rustploy/config.toml.bak
sudo sed -i '/^\[secrets\]$/a recovery_recipient = "age1YOUR_PUBLIC_KEY"' /etc/rustploy/config.toml
sudo python3 -c "import tomllib; tomllib.load(open('/etc/rustploy/config.toml','rb')); print('TOML valid')"
sudo systemctl restart rustployd
```

<Aside type="caution" title="By hand, only applies to secrets saved afterwards">
  Pasting `recovery_recipient` into `config.toml` does not re-encrypt what already exists (generating from the interface
  does). For an old secret to become readable by the recovery key, **save it again** with the same name.
</Aside>

## What to keep off the server

| What | Why |
|---|---|
| `/etc/rustploy/age.key` (or the `config.toml` `age_identity`) | opens every secret |
| The recovery **private** key | opens the secrets even without the server |
| `/etc/rustploy/config.toml` | API token, domains, ACME (and the identity, if it lives there) |
| `/var/lib/rustploy/db` | the entire state (projects, services, encrypted secrets) |

Keep the recovery private key **separate** from the rest: a backup that puts the database, the identity and the
recovery key together opens everything for whoever steals it. See also [Backup and restore](/en/guias/backup/).

## What if I lose...

- **`age.key`, but I have the recovery key (and the secrets were saved after configuring it):** the secrets still open with it.
- **`age.key` and I have no recovery key:** the stored secrets **do not come back**. Recreate them.

## What is not to be confused with these keys

- **`[api] token` and `connection_token`:** they only authenticate whoever talks to the API. They encrypt nothing. See [Server security](/en/operacao/seguranca-do-servidor/).
- **The release signing keys (minisign):** they only confirm a package comes from the maintainer. Nothing to do with your secrets.
