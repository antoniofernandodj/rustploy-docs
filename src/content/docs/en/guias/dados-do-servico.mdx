The service's **Data** tab takes its **data** to an `.rpdata` file and brings it back into another service
of the same kind, on the same server or another. The service **configuration** goes separately
([Copy a service](/en/guias/copiar-servico/)): create the service at the destination first, then import the data.

<Aside type="caution" title="Master key only">
  A data package holds everything an agent must never see (user passwords, your customers' data). Export
  and import require the **master key**; a visitor (agent, MCP) only sees the plan. The package can be
  **encrypted with `age`**: on by default when a recovery key (`recovery_recipient`) is configured, and it opens on the source server or any server restored with that identity/recovery key. To take it to a server without that identity, untick **Encrypt the package**. In the clear, treat the file like a database backup.
</Aside>

To do this **automatically and on a schedule**, sending to S3, see [Data backup to S3](/en/guias/backup-no-s3/): it is the
same package, with scheduling, retention and one-click restore.

## What goes in the package

| Service | What goes | How |
|---|---|---|
| Postgres, MySQL, MariaDB, MongoDB | a **logical dump** of the database | made inside the service's own container, while it keeps running |
| Anything else with volumes (Redis, Kafka, uploads…) | a **tar** of each volume | the service is **stopped** during the copy and restarted afterwards |
| No volumes | nothing | the tab says there is no data |

Databases use a logical dump because a tar of a running database directory can come out corrupted and only
works for the same engine version. A **stopped** database cannot be exported: start it first. **Shared**
database servers are not covered yet.

Of the server folders a service mounts, only the ones it declares are included, never Rustploy's own
(`/etc/rustploy`, `/var/lib/rustploy`) nor system ones.

## Export

1. Open the service → **Data** tab. The list shows what will be taken (`BD` = database, `VOL` = volume).
2. **Export data** and keep the `.rpdata`.

## Import

1. On the destination service (already created, of the **same kind**) → **Data** tab → choose the `.rpdata`.
2. **Check package**: Rustploy verifies integrity (SHA-256) and shows what will be replaced. Nothing changes yet.
3. **Replace the data** and confirm.

Safety rules:

- the package only enters a service that has the same parts; a different engine (MySQL ↔ MariaDB included) is refused, and the destination version cannot be older than the source's;
- everything is checked **before** touching any volume;
- before replacing, Rustploy keeps the current content; if anything fails midway, it **puts back** what it already swapped;
- for a database, the database is **recreated** from the dump on Postgres and MySQL/MariaDB (whatever was not in the package goes away); on MongoDB only the package's collections are replaced;
- for a database, import does **not** stop the service (the restore needs it up): stop whatever uses it first. At the end Rustploy compares per-table counts with the export — differences are normal if the source database was receiving writes during the dump;
- for a plain volume, the service is stopped during the swap and restarted afterwards.

## Mount volumes and adopt an orphan

At the top of an Application service's **Data** tab is the **VOLUMES** list: what the service mounts and
where. To mount a new one:

- **existing volume**: the list shows the volumes without an owner, **orphans** first (*"orphan: db (shop),
  11/24/2026"*). Picking an orphan **adopts** the data of a deleted service: the new service sees the files
  that were there;
- **or a new name**: a named volume is created on the next deploy, already owned by the service;
- **or an absolute folder** on the server (`/srv/uploads`). System folders and Rustploy's own are refused.

Give the **path in the container** (`/data`) and, if needed, **read-only**, and click **Mount**. **✕**
unmounts (it asks for confirmation); the data stays on the server. Mounting and unmounting apply on the
**next deploy**.

A volume that already belongs to another service is refused: two services on the same volume corrupt the
data. Compose services declare their volumes in their own file, so the list does not show for them.

**Volumes**, in the sidebar, shows only the volumes (the data), one card per volume: name, size, state
(**in use**, **unused** or **orphan** with the service and date it came from), a **backup on** badge when
there is a [backup to S3](/en/guias/backup-no-s3/) and **who mounts it**: *"db (shop) →
/var/lib/postgresql"*, with *"· borrowed"* when the stack only uses a volume that already existed.

**Orphans only** filters; **Show anonymous** includes the unnamed volumes the engine creates on its own
(hidden by default). On a volume nobody uses:

- **Adopt in a service**: pick an Application service and the path in the container and click **Mount**.
  It applies on that service's next deploy (the same as mounting from the Data tab);
- **Delete**: asks for confirmation. The data is gone, for good.

## In a Compose stack: use an existing volume

<Shot
  src={composeVolume}
  alt="Compose editor with the Use existing volume panel open: a list of volumes and the Cancel and Insert buttons."
  caption="Insert only changes the editor's text; nothing is saved until Save compose."
/>

A Compose stack declares its volumes in its own file. To have it use a volume that already exists (the
database of a deleted service, for example), on the **General** tab click **Use existing volume**, pick
the volume (orphans first) and **Insert**. Rustploy adds to the file, without touching the rest:

```yaml
volumes:
  # volume existente (adicionado pelo Rustploy): monte com `- banco_antigo:/caminho` num serviço
  banco_antigo:
    external: true
    name: banco_antigo
```

All that is left is mounting it in the stack service that will use it
(`- banco_antigo:/var/lib/postgresql/data`) and clicking **Save compose**. It applies on the next deploy.

## Borrowed volumes

A volume declared with `external: true` is **borrowed**: it already existed and the stack only uses it.
It shows the stack as its owner (it is not "loose"), but deleting the service with **Delete the data**
only deletes the stack's **own** volumes. Borrowed ones only go if you answer **Delete the borrowed
ones** to the third question; kept, they become orphans, with their origin, and another stack can use them.

## Through the API

`ServiceDataPlan{service_id}` returns the plan (allowed for the observer level). The bytes go through
`GET /api/services/<id>/data/export?stop=true|false` and `POST /api/services/<id>/data/import?confirm=true|false`
(without `confirm`, it only checks).
