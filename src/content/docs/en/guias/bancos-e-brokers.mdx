The **Novo serviço** (New service) wizard creates ready-made databases, brokers and storage, with generated credentials
and a connection URL. They are Docker Compose stacks underneath.

## What exists

| Type | Options | Default image | Port |
|---|---|---|---|
| **Database** | PostgreSQL | `postgres:18` | 5432 |
| | MySQL | `mysql:8` | 3306 |
| | MariaDB | `mariadb:11` | 3306 |
| | MongoDB | `mongo:8` | 27017 |
| | Redis | `redis:7` | 6379 |
| **Broker** | Kafka | `apache/kafka:3.9.0` | 9092 |
| | RabbitMQ | `rabbitmq:4-management` | 5672 |
| | NATS | `nats:2` | 4222 |
| **Storage** | RustFS | `rustfs/rustfs:latest` | 9000 |
| | MinIO | `cgr.dev/chainguard/minio:latest` | 9000 |

<Aside type="caution" title="MongoDB 8 and new kernels">
  The `mongo:8` image does not start on Linux kernels 6.19 or newer (a known problem in MongoDB itself). On
  those servers, change the image to `mongo:7` in the form.
</Aside>

## Create

<Steps>
1. In the project, **+ Novo serviço**, and choose **Database** (or **Broker**).
2. Pick the engine.
3. Fill in the form. The service name is the only required field; user and password are **generated** if you leave them blank: the password is generated by the server, with 24 random characters, and stored **encrypted** as a service [secret](/en/guias/variaveis-e-secrets/) — it is not in the creation response nor in the state as plain text. To see it, use the secret's **👁** (it is audited). Depending on the engine you also see **database name**, **user**, **password**, **root password**, the **image** and, on MongoDB, **Use Replica Sets**.
4. Create it and run the **Deploy**.
</Steps>

## S3 storage (RustFS and MinIO)

**New service → Storage** creates an S3-compatible object server, following the same logic as databases: a Compose
stack (`rp_<name>`) with the credentials **generated and stored encrypted**.

| Option | Default image | S3 API | Console |
|---|---|---|---|
| **RustFS** | `rustfs/rustfs:latest` | 9000 | 9001 |
| **MinIO** | `cgr.dev/chainguard/minio:latest` | 9000 | 9001 |

- **User** is the *access key* and **Password** is the *secret key*. Leave both empty and the server generates them: the
  default user (`rustfsadmin` or `minioadmin`) and a strong 24-character password.
- The application uses the internal endpoint `http://rp_<name>:9000`, shown in the service's **Connection** tab. The keys
  are service [secrets](/en/guias/variaveis-e-secrets/) (`RUSTFS_ACCESS_KEY`/`RUSTFS_SECRET_KEY`, or
  `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`). To give them to an application **without copying the value**, reference the
  secret in the application's variable (`S3_ACCESS_KEY_ID` = `<secret:RUSTFS_ACCESS_KEY>`) or use ✏️ to rename the key.
- The generated Compose does **not** open CORS (`*`). If you need CORS, add it to the service's Compose.

<Aside type="caution" title="MinIO image">
  `minio/minio` and `minio/mc` are **no longer pullable** (Docker Hub and Quay answer *access denied*). That is why the
  default is the Chainguard build, which uses the same command and variables. If you prefer another source, change the
  image in the form. The `minio` template in the *Templates* catalog still points at the old image.
</Aside>

### Create a bucket

The Storage **does not create a bucket by itself**. The way that does not expose the key is a **job** with the Storage as
its trigger service: the job inherits its environment (secrets decrypted only in memory). Under **Jobs**, create a job in
the project, with the Storage as *trigger service* and `bucket` as the main service, and run it:

```yaml
services:
  bucket:
    image: docker.io/curlimages/curl
    entrypoint: ["/bin/sh", "-c"]
    command: ["curl -sS -f -X PUT --aws-sigv4 aws:amz:us-east-1:s3 --user \"$$AK:$$SK\" -o /dev/null -w 'HTTP %{http_code}\\n' http://rp_files:9000/my-bucket"]
    environment:
      AK: ${RUSTFS_ACCESS_KEY}
      SK: ${RUSTFS_SECRET_KEY}
```

For MinIO, swap the two variables for `${MINIO_ROOT_USER}` and `${MINIO_ROOT_PASSWORD}`. The `HTTP 200` output means the bucket
exists; running the job again is safe.

<Aside type="caution" title="Why curl and not aws-cli">
  `aws-cli` (botocore) rejects host names with `_` and answers `Invalid endpoint: http://rp_files:9000`, and services'
  internal names are `rp_<name>`. `curl --aws-sigv4` accepts the name.
</Aside>

<Aside type="note" title="This is the administrator key">
  Today the application would use the Storage's **root** key. A dedicated key, with permission on the bucket only, is not
  generated by Rustploy yet.
</Aside>

## How the application connects

Open the service's **Connection** tab: it shows the **internal host** and **connection URL**, ready to copy. Use
the internal URL in the environment variables of applications in the **same project**.

To wire up the application, put the URL in a variable (for example `DATABASE_URL`) and redeploy it. Prefer
storing the password as a [secret](/en/guias/variaveis-e-secrets/).

If several projects need the same database, see the [shared database](/en/guias/banco-compartilhado/).

## Access from outside the server

By default the database is **only reachable from inside** the project. In the **desktop app**, the form has the
option **"Gerar URL de conexão externa (porta e firewall automáticos)"** (Generate external connection URL,
automatic port and firewall). When you tick it, Rustploy:

1. allocates a free port from the `[external_ports]` range (default 20000–20999);
2. opens it in `ufw`, through the `rustployd-fw` helper;
3. shows the **External URL** on the **Connection** tab.

<Aside type="caution">
  This makes the database reachable from the **internet**, protected only by its password. Use a strong
  password, and consider restricting by IP in the firewall. The web UI does not yet offer this option in the wizard.
</Aside>

The **Ingress** screen lists the external TCP ports in use.

## Backup

Rustploy **does not back up the data** in databases. See [Backup](/en/guias/backup/).
