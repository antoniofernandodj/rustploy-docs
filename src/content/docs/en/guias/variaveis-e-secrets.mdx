## Two layers

| Layer | Where to edit | Applies to |
|---|---|---|
| **Project** | project → **Variáveis** (Variables) tab | all the project's services |
| **Service** | service → **Environment** tab | only that service |

If the same key exists in both, **the service's wins**.

Both places have a **`.env` editor**: one `KEY=value` line per variable, with support for comments (`# …`)
that are preserved.

<Aside type="note">
  Variables are handed to the container **when it is created**. After changing a variable, run a new
  **Deploy** for it to take effect. **Reload** is not enough. Full rules (precedence, build, Compose) in
  [How environment variables are resolved](/en/conceitos/variaveis-de-ambiente/).
</Aside>

## Secrets

Sensitive values (passwords, API keys, tokens) go into a **secret**, which is encrypted before it reaches the database.

### Create

In the project, on the **Secrets** tab: enter the **name** (`API_KEY`) and the **value**. Saving encrypts the
value right away. The list shows only the name. To change the value, save another secret with the
**same name**.

### See the value

In the GUI and the web UI, every secret (project or service) has a **👁** button. It asks for confirmation and
shows the value on the row itself (**🙈** hides it, **📋** copies it). The value stays only in the screen's memory
and disappears when you switch project or service.

Every read is **recorded in the server audit**: who, which secret and when, never the value. AI agents (MCP)
**cannot** read a secret's value.

### Use in a variable

A variable can reference a secret instead of holding the value. In any of these ways:

- in the **project variables**, turn on **"usar secret"** (use secret) when adding the variable and click the secret's name;
- on the service's **Environment** tab, put `<secret:API_KEY>` as the value;
- in the `.env` editor, write `API_KEY=<secret:API_KEY>`.

After saving, the variable appears as `secret:API_KEY`: a reference, not the value. Rustploy decrypts the value
only at deploy time. On an application service it stays in memory; on a Compose stack it goes through a temporary
`.env` file (see the [details](/en/conceitos/variaveis-de-ambiente/#compose-via-the-env-file)).

### Rename

The **✏️** on a variable's row changes its **key**; the ✏️ on a secret's row changes its **name**. In neither case does
the value pass through the screen, and that holds for MCP users too: an agent can rename without seeing anything.

- **Variable**: only the key changes; the value (plain or a reference to a secret) stays as it is, and the `.env`
  editor comments above it move along. Useful to align names across services, for example `RABBITMQ_DEFAULT_PASS` (the
  broker's) to `RABBITMQ_PASS` (the code's).
- **Secret**: the name changes **and** every variable that pointed to it now points to the new name, in the same
  operation. A **project** secret does not touch services that have their own secret with the same name: in those, the
  reference already resolved to the service's one and keeps working.
- Both **refuse** a name that already exists in the same place (nothing is overwritten) and invalid names: a variable
  accepts only letters, digits and `_`, not starting with a digit; a secret accepts letters, digits, `_`, `.` and `-`.

### Remove

The `✕` on the secret's row deletes the value, with no way to recover it. Variables that reference it receive
**empty text** on the next deploy; the deploy does not fail, the container just starts without the value. The
same happens if you mistype a secret's name.

### A secret for cloning a private repository

The same mechanism serves the clone token. See [Git](/en/guias/git/).

## What is and is not protected

| Protected | Not protected |
|---|---|
| The value never goes to the database in plain text | Whoever has the API token **reads the decrypted values** (the API returns the resolved variables) |
| Listing secrets returns only names | Whoever gets into the container sees the environment variables |
| Clone URLs appear as `***` in logs | A manifest export with `Plain` values carries the plain values |

<Aside type="danger" title="Back up the age identity">
  Secrets are encrypted with the server's `age` identity (`/etc/rustploy/age.key` or `age_identity` in
  `config.toml`). Without it, the stored values are unrecoverable. Keep a copy off the server and set up a
  recovery key. See [Keys and secrets](/en/guias/chaves-e-segredos/).
</Aside>

## Automatic backup

The daemon writes, by default every 60 s, snapshots of project and service variables to
`<db_path>/env_backups/`, which protects against a mistaken edit.
