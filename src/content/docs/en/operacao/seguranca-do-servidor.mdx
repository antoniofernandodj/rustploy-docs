This page describes what Rustploy protects, what it does **not** protect and what you should do on the server.

## The API token is everything

The API uses **a single Bearer token, with no scope**. Whoever has it can do **anything**: create projects, read
**decrypted** variables and secrets, start and stop containers, delete services and databases. There is no
read-only mode, no per-user access, and no confirmation on destructive commands.

The same goes for the **connection token**, which carries the API token, and for the
[AI agent](/en/agentes/seguranca/)'s access.

**Treat the token as the server's root password**: it leads to running containers with whatever you mount in them.

- Use a long, random value (`openssl rand -hex 32`).
- Change it if it leaks: edit `[api].token`, restart the daemon, and sign in again on the clients.
- Do not put it in Git. Keep it in `config.toml` (mode `640`, owner `rustploy`) or in `/etc/rustploy/environment`.

### The bind guard

The daemon **does not start the API** if `bind_address` is not loopback and there is no `token`. It logs an error
and **keeps running without an API**: the dashboard and agents are down. Look for the message `listener NÃO
iniciado` (listener NOT started) in `journalctl`.

## Exposing the API

By default the API listens on `127.0.0.1`. When opening it to the internet:

- **Use HTTPS.** Set `[api].domain` so the daemon itself terminates TLS on the API port (Let's Encrypt). Without it, the token travels in **plain text**.
- **Reduce the surface.** If only you administer it, leave the port closed to the world and reach it over a **VPN** or an **SSH tunnel** (`ssh -L 9797:127.0.0.1:9797 server`).
- Webhooks need public access to the same port; the `/webhook/…` path is separate and does **not** open the API.

## What Rustploy isolates

- **Per-project networks.** Each project has its own Docker network; containers of different projects **cannot see each other**. The proxy is the only entry point.
- **No extra privileges.** Service containers use no `--privileged` and no additional capabilities.
- **The shared database** is the controlled exception: Rustploy connects the database server to the networks of the projects **you authorize**, with an alias of its own, and each project has a separate user and database. See [Shared database](/en/guias/banco-compartilhado/).

This does **not** protect against what is inside the container: a vulnerable application is still vulnerable. And
a Compose service or a job is your YAML: it can mount `/var/run/docker.sock` or use `privileged: true`, and
Rustploy does not prevent it.

## Secrets

- They are encrypted with `age` before going to the database; listing returns only names.
- The **master key** lives at `/etc/rustploy/master.key`. The file is created with the process's default permissions; what protects it is the `/etc/rustploy` directory, with mode `750` and owner `rustploy`. Keep it that way, and keep a copy **off the server**.
- On Compose stacks and jobs, decrypted values pass through a temporary `.env` on disk. See [How environment variables are resolved](/en/conceitos/variaveis-de-ambiente/#compose-via-the-env-file).
- Passwords generated by **templates** stay as plain variables, not as secrets.

## The daemon's user and the `docker` group

`rustployd` runs as the **`rustploy`** system user, with no shell and no home directory, in the **`docker`** group.
Being in the `docker` group is equivalent to having **root on the server**: whoever controls the daemon controls
Docker. The systemd unit reduces what it can: `NoNewPrivileges`, `PrivateTmp` and only the
`CAP_NET_BIND_SERVICE` capability (to listen on ports 80 and 443).

## The firewall helper

Opening a port in `ufw` requires root, so that lives in a separate process, **`rustployd-fw`**:

- it runs as root, but is only **activated by a socket** (`/run/rustploy/fw.sock`), accessible to root and the `rustploy` group (mode `0660`);
- it accepts only two requests, *allow* and *deny* of a **TCP port**;
- it **refuses any port outside the `[external_ports]` range** (default 20000–20999) and only talks to `ufw`;
- it runs with a read-only file system, except where `ufw` writes.

Exposing a database **opens the port to the internet**, protected only by its password. Restrict by IP in `ufw`
itself when you can.

## The update helper

Installing a `.deb` needs root, and the daemon does **not** have root. A second process installs it, **`rustployd-update`**,
under the same rule as the firewall helper: minimal surface.

- it is only **activated by a socket** (`/run/rustploy/update.sock`, group `rustploy`, mode `0660`), serves **one request** and exits;
- it **opens no network connection**: the daemon downloads the package, and the helper only checks and installs (so it runs without a network);
- it accepts only two requests, *install* and *rollback*, and **only installs the `rustployd` package**: a signed `.deb` of
  another product (such as `rustploy-gui`) is refused;
- it only installs what is **signed** with the project key (minisign/ed25519, embedded in the helper). The release's
  SHA-256 is not enough, because it comes from the same place as the file: whoever swapped the release would swap both. The
  signature carries the package name, version and architecture, and the helper checks they match the `.deb`;
- it **never installs a version that is not newer** than the installed one (an old, legitimate, signed package does not come back);
- it copies the file to a root-only directory **before** checking, so the daemon cannot swap it after the check;
- after installing, it waits for the service to stay stable for a few seconds and, if it crash-loops, **restores the
  previous binaries** by itself.

The API token can use `ApplyUpdate`, but **the MCP agent cannot** request an update unless you turn on `allow_agent_apply`
in [`[update]`](/en/instalacao/config-toml/#update-optional). If the signing key leaked, whoever held it could publish a
package every installation would accept as root: that is why it stays only on the owner's machine, with a password, never in CI.

## The desktop app helper

The app runs on **your machine**, not on the server, and its update follows the same idea as the daemon's with one
difference: there is no resident service. When you click **Atualizar app**, the app downloads the `.deb` and the signature to
its own cache (`~/.cache/rustploy-gui/updates`) and runs `pkexec /usr/libexec/rustploy-gui-update install …`; the system shows
the password dialog, the helper installs and **exits**. Nothing runs as root between one update and the next.

The guarantees are the daemon helper's: it opens no network, only installs the `rustploy-gui` package, only if it is
**signed** with the project key, and never a version that is not newer. Besides that:

- it only reads files **directly from the calling user's cache**. The directory comes from `PKEXEC_UID` resolved in the user
  table, not from the `HOME` variable, which the user controls; a package in **another** person's cache is refused;
- it refuses symbolic links and copies the file to a root-only directory before checking the signature;
- the polkit policy (`br.com.rustploy.gui-update`) authorizes **a single program**, `/usr/libexec/rustploy-gui-update`,
  asking for the administrator password (`auth_admin_keep`: valid for a few minutes).

Without `pkexec` on the system, or in an app that did not come from the `.deb`, the button does not appear and the tab only
shows the install command.

## Built-in registry

Every route requires authentication, even on loopback. Use **pull** tokens where you only download and **push**
only in CI. The secret appears only once. See [Registry](/en/guias/registry/).

## Webhooks

The token has 48 hexadecimal characters, is unique per service and is compared in constant time. The URL works
like a password: store it as a secret in your CI and use **Regenerar** (Regenerate) if it leaks.

## Hardening checklist

1. A **strong** API token, only in `config.toml` (`640`) or in `/etc/rustploy/environment`.
2. `[api].domain` with HTTPS, **or** the API on loopback only with a VPN or SSH tunnel.
3. The server firewall (ufw or the provider's): open only 22, 80, 443 and, if needed, 9797.
4. SSH by **key**, no password, and no root login.
5. [Backup](/en/guias/backup/) of `master.key` and `/var/lib/rustploy`, **off** the server.
6. System and Docker updates kept current.
7. Images from trusted sources; do not mount `docker.sock` in containers.
8. Strong passwords on externally exposed databases, or do not expose them.
9. Give AI agents only what you would be willing to give an administrator.
