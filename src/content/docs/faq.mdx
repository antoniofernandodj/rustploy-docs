## Sobre o Rustploy

### O que é o Rustploy?

O Rustploy é um PaaS self-hosted de nó único, escrito em Rust, que faz deploy de containers Docker com troca sem downtime, proxy reverso com HTTPS automático, registry embutido, jobs agendados e um servidor MCP. Roda como um binário só, o `rustployd`, numa VPS com Docker. Veja [O que é o Rustploy](/comece/o-que-e/).

### Para que o Rustploy não serve?

O Rustploy não serve para mais de um servidor, para centenas de containers nem para builds sem Dockerfile. Ele gerencia **uma** máquina Linux com Docker, não faz cluster, e construir a partir de código exige um `Dockerfile` (não há buildpacks). Para vários hosts, veja os [comparativos](/comparativos/visao-geral/).

### Quanta memória o Rustploy usa?

O alvo do projeto é ficar abaixo de 50 MB de RAM em repouso, mas esse número é uma meta e não uma medição publicada. O daemon, o proxy, o banco SQLite e o registry rodam num processo só. O que pesa de verdade são as suas aplicações e os builds, então planeje pelo menos 1 GB de RAM na VPS.

### O Rustploy é gratuito? Qual a licença?

Sim, o Rustploy é gratuito e de código aberto, com licença MIT declarada nos `Cargo.toml` dos três repositórios (`rustploy-daemon`, `rustploy-gui` e `rustploy-shared`). O código está em github.com/antoniofernandodj/rustploy.

### Preciso saber Docker para usar?

Sim, a documentação parte do princípio de que você já conhece imagem, container, rede, volume, Dockerfile e Docker Compose. O Rustploy automatiza o que você faria à mão com o Docker. A tabela [Do Docker para o Rustploy](/comece/docker-para-rustploy/) traduz cada conceito.

### Em quais sistemas o Rustploy roda?

O daemon roda em Linux com systemd e Docker Engine, em x86_64 ou aarch64. O app desktop tem versões para Linux e Windows. Não há suporte a macOS no app desktop, mas a web UI funciona em qualquer navegador.

## Instalação e acesso

### Como instalo o Rustploy?

Com um comando, na VPS Debian ou Ubuntu: `curl -fsSL https://raw.githubusercontent.com/antoniofernandodj/rustploy/main/install.sh | sudo sh`. Ele baixa o `.deb` do `rustployd` da última release do GitHub, confere o SHA-256, instala, gera um token e mostra o token de conexão. O pacote cria o usuário `rustploy`, o serviço systemd e o helper de firewall. Veja [Instalação rápida](/instalacao/instalacao-rapida/). Enquanto não houver release publicada, o instalador avisa e não instala nada: use o `.deb` gerado com `make deb-rustploy` ([Instalar o daemon na VPS](/instalacao/instalar-daemon/)).

### Preciso instalar o git no servidor?

Sim, se algum serviço usar a fonte Git: o clone usa o comando `git` do servidor, e o pacote `.deb` não o declara como dependência. Instale com `sudo apt-get install git`. Sem ele o deploy falha com "falha ao iniciar git". Veja [Fazer deploy a partir de Git](/guias/git/).

### Onde pego o token de conexão?

O token de conexão sai de `sudo rustployd access-key` na VPS, de `[api].connection_token` no `config.toml`, ou de Settings → Web Server no app. Ele é o base64 de `host:porta::token` e só existe se `[api].token` estiver configurado. Veja [Primeiro acesso](/instalacao/primeiro-acesso/).

### Como acesso o painel de outra máquina?

Defina `[api].bind_address = "0.0.0.0"` e um `[api].token` forte no `config.toml`, reinicie o daemon e abra a porta 9797 no firewall. O daemon se recusa a subir com bind público e sem token. Para HTTPS, configure `[api].domain`. Veja [Instalar o daemon na VPS](/instalacao/instalar-daemon/).

### Editei o config.toml e nada mudou. Por quê?

Provavelmente o arquivo tem um erro e o daemon o ignorou **em silêncio**, usando os padrões. Um TOML inválido, uma seção obrigatória faltando ou um valor com o tipo errado (`port = "9797"` com aspas) descartam o arquivo inteiro, sem aviso no log. Confira com `sudo rustployd access-key`: se disser que não há token, o arquivo não foi lido. Veja [O arquivo config.toml](/instalacao/config-toml/).

### Como atualizo o Rustploy?

Instale o `.deb` novo por cima do antigo com `sudo dpkg -i`. Seus dados em `/var/lib/rustploy`, o `config.toml` e a `master.key` são preservados, e os containers dos serviços continuam rodando. Veja [Atualizar o Rustploy](/instalacao/atualizar/).

## Deploy

### Criei o serviço, mas nada está no ar. Por quê?

Criar um serviço não faz deploy: ele nasce parado e vazio. Abra o serviço, configure a origem (Git, imagem ou zip), a porta e o healthcheck, e clique em **Deploy**. Veja o [tutorial do primeiro deploy](/tutorial/primeiro-deploy/).

### Por que meu deploy falhou?

A causa fica no **build log** do deploy, na linha `==> Erro em [Estado]: …`. No app desktop, abra o serviço, aba Deployments, e clique em **≡** na linha do deploy. As causas mais comuns são Dockerfile não encontrado, `git` ausente no servidor e healthcheck que não passa. Veja [O ciclo de vida de um deploy](/conceitos/ciclo-de-vida/).

### Meu deploy fica parado em Pending. O que é isso?

O Rustploy executa **um deploy por vez** no servidor inteiro, e os outros esperam na fila. Veja a fila na tela Deploy Engine. Se a fila estiver **pausada**, os deploys esperam até você retomar. Um deploy enfileirado pode ser promovido ao topo ou cancelado. Veja [A fila de deploys](/guias/fila-de-deploys/).

### Como volto para a versão anterior?

Redeploye a versão anterior: ponha de volta a imagem, a branch ou o commit que funcionava e clique em **Deploy**. O botão Rollback não redeploya: ele só localiza o deploy anterior. Se um deploy falhar no healthcheck, o Rustploy volta sozinho para o container antigo. Veja o [tutorial](/tutorial/primeiro-deploy/).

### O deploy é realmente sem downtime?

Sim, desde que o healthcheck esteja configurado. O container novo sobe ao lado do antigo, passa no healthcheck, e só então o proxy troca a rota de uma vez. Um serviço novo nasce com healthcheck **None**, e nesse caso o Rustploy só confere que o container subiu, não que o app responde. Configure um healthcheck HTTP. Veja [Healthcheck](/guias/healthcheck/).

### Posso fazer deploy a cada push no Git?

Sim, com o **webhook de deploy**: cada serviço Application tem uma URL secreta, e um `POST` nela dispara o deploy. Funciona com GitHub, GitLab, Gitea, Docker Hub e GitHub Actions, e pushes em outras branches são ignorados. A URL só aparece depois do primeiro deploy. Veja [Webhooks de deploy](/guias/webhooks/).

### Meu `ARG` do Dockerfile chega vazio. Por quê?

O `docker build` do Rustploy roda **sem** as variáveis do projeto ou do serviço: não existem *build args*. As variáveis só chegam ao container em execução. Leia o valor em tempo de execução ou, se o build precisar dele, use uma stack Compose com `build.args`. Veja [Como as variáveis são resolvidas](/conceitos/variaveis-de-ambiente/).

### Mudei uma variável de ambiente e nada mudou. Por quê?

As variáveis são entregues ao container quando ele é **criado**, então a mudança só vale no próximo **Deploy**. O Reload apenas reinicia o container existente e não aplica variáveis novas. O mesmo vale para trocar o valor de um secret. Veja [Variáveis de ambiente e secrets](/guias/variaveis-e-secrets/).

### Meu monorepo não acha o Dockerfile. O que ajusto?

Aponte o **CONTEXT PATH** para a pasta do app (por exemplo `apps/web`) e o **DOCKERFILE** para o arquivo dentro dela. O caminho do Dockerfile é relativo ao contexto, e o Rustploy confere que ele existe antes de chamar o Docker. Os campos **WATCH PATHS**, **BUILD PATH** e **BUILD STAGE** aparecem na tela, mas o deploy ainda não os usa. Veja [Fazer deploy a partir de Git](/guias/git/).

### Dá para fazer deploy sem Dockerfile?

Não para construir a partir de código: o Rustploy não tem buildpacks e exige um `Dockerfile`. Sem Dockerfile você pode usar uma imagem pronta de um registry, uma stack Compose ou um template do catálogo. Veja [Serviço e fontes](/conceitos/servico-e-fontes/).

## Domínios, rede e HTTPS

### Meu domínio responde 502. Como diagnostico?

Um 502 significa que o proxy achou a rota, mas o container não respondeu. Veja a tela Ingress: se o domínio não aparece, nenhum deploy registrou a rota; se a porta de destino está errada, corrija a porta do domínio na aba Domains. Confira também se o app escuta em `0.0.0.0` e se o healthcheck passa. Veja [Diagnosticar um erro 502](/guias/diagnosticar-502/).

### O certificado HTTPS não sai. O que verifico?

Verifique, nesta ordem: o DNS do domínio aponta para o servidor, `ingress.acme.enabled` é `true` com um `email`, as portas 80 e 443 estão abertas para a internet, e o serviço chegou a `Live` (o certificado é pedido depois do deploy). O Let's Encrypt precisa alcançar a porta 80 pelo nome do domínio. Veja [Domínios e HTTPS automático](/guias/dominios-e-tls/).

### Como minha aplicação encontra o banco de dados?

Dentro do projeto, os serviços se alcançam pelo nome na rede do projeto: um serviço Application responde como `rp_<nome>`, e um serviço Compose pelo nome do serviço **dentro do YAML**. A aba Connection do banco mostra a URL interna pronta para copiar. Veja [Rede e nomes](/conceitos/rede-e-nomes/).

### Como acesso um banco de fora do servidor?

Abra uma porta TCP do host: na aba Domains do serviço use **PORTA TCP DO HOST** (Salvar porta ou Automática), ou marque a opção de URL externa no assistente da GUI. O Rustploy aloca uma porta da faixa 20000–20999 e a libera no firewall. Isso expõe o banco à internet, protegido só pela senha: use uma senha forte. Veja [Bancos e brokers](/guias/bancos-e-brokers/).

### Um serviço pode ter vários domínios?

Sim, cada serviço pode ter vários domínios, cada um com a própria porta de container e com ou sem TLS. Eles ficam na aba Domains. Em uma stack Compose, só um container atende o domínio: defina o alvo de ingress se o escolhido por padrão estiver errado. Veja [Domínios e HTTPS automático](/guias/dominios-e-tls/).

## Dados, backup e segurança

### O Rustploy faz backup dos meus bancos de dados?

Não, o Rustploy não faz backup dos dados dos seus bancos nem dos volumes. Use um job agendado que roda `pg_dump`, `mysqldump` ou `mongodump` para um caminho do host e copie esse caminho para fora do servidor. Faça também backup do estado do próprio Rustploy e da `master.key`. Veja [Backup e restauração](/guias/backup/).

### Meus serviços voltam sozinhos depois de reiniciar o servidor?

Provavelmente não. Pelo código, os containers são criados com a política de reinício `no`, e ao subir o daemon marca como parados os serviços sem container rodando. O plano de iniciar tudo no boot ainda não foi implementado. Depois de um reboot, faça Deploy dos serviços. Confira no seu servidor antes de depender disso. Veja [Monitoramento, saúde e reinício automático](/operacao/monitoramento-e-saude/).

### Existe somente leitura ou controle de acesso por usuário?

Não, a API usa um único token de administrador, sem escopo e sem usuários. Quem tem o token faz qualquer coisa, inclusive ler secrets decifrados, e comandos destrutivos não pedem confirmação. Proteja o token como a senha de root, use HTTPS e, se possível, VPN. Veja [Segurança do servidor](/operacao/seguranca-do-servidor/).

### O token vazou. O que faço?

Troque `[api].token` no `config.toml`, reinicie o daemon e entre de novo nos clientes. O `connection_token` se regrava sozinho. Se o token estava em agentes de IA, remova e registre o MCP de novo. Veja [Segurança do servidor](/operacao/seguranca-do-servidor/).

### Perdi a master.key. Consigo recuperar os secrets?

Não: sem a chave mestra em `/etc/rustploy/master.key`, os secrets gravados não podem ser decifrados, e um backup do banco sozinho não resolve. Guarde uma cópia da chave fora do servidor. Você precisará recriar os secrets. Veja [Variáveis de ambiente e secrets](/guias/variaveis-e-secrets/).

### Onde ficam os logs da minha aplicação?

O log de runtime é lido do Docker **ao vivo** e não é guardado: quando um deploy troca o container, o log do antigo some. Abra-o na aba Logs do serviço. O **build log** de cada deploy fica guardado. Para histórico da aplicação, envie os logs para fora do servidor. Veja [Janelas de logs](/interface/logs/).

## Agentes de IA e MCP

### Como conecto o Claude Code ao Rustploy?

Em Settings → Web Server, use o botão **Conectar um agente (Claude Code)** para copiar o comando `claude mcp add --transport http rustploy https://HOST:PORTA/mcp --header "Authorization: Bearer <token>"` e rode-o no terminal. Depois abra uma sessão **nova** do Claude Code. Veja [Conectar o Claude Code ao Rustploy](/agentes/conectar-claude-code/).

### O que um agente de IA consegue fazer no meu servidor?

Um agente consegue listar serviços, disparar deploy e esperar o resultado, ler o build log, diagnosticar um 502 e executar qualquer comando do protocolo pela ferramenta `rpc`. São nove ferramentas MCP. O acesso é o mesmo de um administrador. Veja [Operar o Rustploy com agentes de IA](/agentes/visao-geral/) e a [referência das ferramentas](/agentes/ferramentas/).

### É seguro dar o token a um agente de IA?

Só com cautela: o token é de administrador, o servidor não pede confirmação em comandos destrutivos (`ServiceDelete`, `Prune*`, `Remove*`) e não existe modo somente leitura. Instrua o agente a descrever e aguardar sua confirmação antes de agir, nomeie cada servidor e use o MCP só em redes de confiança. Veja [Segurança ao usar agentes](/agentes/seguranca/).

## Migração e operação

### Consigo migrar do Dokploy?

Em parte: o importer `rustploy-import` copia projetos, aplicações Git, stacks Compose, variáveis e o primeiro domínio de cada serviço. Ele não converte aplicações de imagem Docker, bancos de dados, secrets nem volumes, e a gravação direta pode apagar serviços de mesmo nome. Rode antes com `--dry-run`. Veja [Migrar do Dokploy](/migracao/dokploy/).

### Como copio um serviço para outro servidor?

Use **Exportar serviço** na tela do serviço para gerar um arquivo e **Importar** no assistente Novo serviço do outro servidor. O serviço é criado sem deploy e nada é sobrescrito. Só a configuração viaja: dados, volumes e secrets não. Para levar o servidor inteiro, use o [manifesto de Infra as Code](/guias/infra-as-code/).

### Qual a diferença entre Deploy, Reload e Rebuild?

**Deploy** faz o ciclo completo (build ou pull, container novo, healthcheck, troca de rota). **Reload** só reinicia o container que está no ar, sem aplicar variáveis nem imagem novas. No app desktop, **Rebuild** chama a mesma função que Deploy. Veja [A tela do serviço](/interface/servico/).

### Devo usar o app desktop ou a web UI?

Tanto faz para o dia a dia: os dois falam com a mesma API. A web UI não exige instalação e funciona no celular como PWA. O app desktop guarda vários servidores, tem bandeja do sistema e avisa quando um deploy termina, mesmo com a janela fechada. Alguns recursos só existem pela API ou pelo MCP. Veja [Instalar os clientes](/instalacao/instalar-clientes/).

### Qual a diferença entre o Rustploy e o Dokploy, o Coolify ou o CapRover?

O Rustploy gerencia uma única máquina com um binário só e proxy próprio, e tem MCP nativo. Os outros três gerenciam mais de um servidor (ou usam Swarm), têm comunidades maiores e mais recursos, como backups e notificações. Veja a [visão geral dos comparativos](/comparativos/visao-geral/).
